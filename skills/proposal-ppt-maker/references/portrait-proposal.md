# 세로형 제안 장표 작성 규칙

## 1. 거버닝 메시지

모든 `portrait` 청사진에 `governing_message`를 작성한다.

- 제목 아래에 배치한다.
- 제안사가 무엇을 어떻게 구현하는지 말한다.
- 구현 결과로 확보되는 효과 또는 통제 수준을 포함한다.
- 발주 요구사항을 그대로 반복하지 않는다.
- 반드시 `니다.`로 끝낸다.
- 분석 메모, 제작 지시, 미확정 표현을 포함하지 않는다.

예시:

> LLMOps와 AI Agent 전 생애주기를 단일 파이프라인으로 통합해 개발 속도와 운영 통제력을 동시에 확보합니다.

## 2. 분석과 가시 콘텐츠 분리

`요구사항 해석`, 내부 판단, 자산 검색 메모, 제작자용 설명은 청사진 작성 전 분석 산출물이다. 최종 장표에 노출하지 않는다.

`source_refs`, 원문 인용, 보호 정량지표, 자산 매핑·fallback 정보도 청사진·세션·검수 보고서용 내부 메타다. 최종 장표에는 `RFP`, `요구사항`, `원문`, `근거`, `출처`, `asset`, `fallback` 등 제작·추적 표현을 노출하지 않고 구현·운영·활용 문장으로 변환한다. 사용자가 원문 인용을 명시적으로 요청한 경우만 예외다.

기간·마일스톤·일정·단계 전환이 원문이나 사용자 지시에 없으면 로드맵·간트·타임라인을 추가하지 않는다. 처리 순서와 일정은 다르므로, 일정 근거 없이 `6개월` 등의 기간을 추정하지 않는다.

모든 PPT 생성은 `와이어프레임 표시 → 사용자 명시 승인 → 최종 렌더링` 순서를 따른다. 승인 전 청사진은 `draft` 또는 `pending`으로 유지하고 최종 PPTX 렌더러를 호출하지 않는다.

| 내부 분석 표현 | 최종 가시 제목 예시 |
|---|---|
| 요구사항 해석 | 핵심 구현 전략 |
| 기술 적용안 비교 | 통합 적용 방안 |
| 운영 검토 | 운영 통제 |
| 검토 필요 | 적용 원칙 또는 기대효과 |

## 3. 정보 밀도

세로형은 반드시 `density: high`로 작성하고 정보 밀도를 가독성 한도까지 높게 유지한다. RFP 근거에서 다음 내용을 가능한 한 빠짐없이 채운다. 큰 빈 패널이나 두세 줄 요약으로 끝내지 않는다.

1. 핵심 구현 전략과 차별점
2. 구성요소, 단계, 연계 흐름
3. 자동화, 관리, 연동, 예외처리 등 세부 기능
4. 권한, 추적, 버전, 품질, 보안, 롤백 등 운영 통제
5. 적용 결론과 기대효과

원문에 내용이 있는데도 요약 두세 줄과 큰 빈 패널만 남기지 않는다. 요구사항·기능·세부 처리·통제·검증 기준·성과·자사 대응을 의미 단위로 나누어 도식·본문·주석에 충분히 담고, 본문은 원칙적으로 16pt 이상을 유지한다.

## 4. 상자보다 도식

모든 텍스트 그룹을 채운 사각형 안에 넣지 않는다. 한 장에서 하나의 주도 도식이 흐름을 만들도록 한다.

- 병렬 전략 3개 이상: chain 또는 repeated nodes
- 통제항목: wheel 또는 hub-spoke
- 두 실행 축: comparison 또는 convergence
- 단계: process, lifecycle, roadmap
- 구성요소: architecture 또는 hierarchy

불릿 옆에 장식 자산을 놓는 것보다 불릿 자체를 도식 노드의 라벨로 바꾸는 방식을 우선한다.

### 첫 레이아웃의 최소 골격

첫 와이어프레임에는 장식을 제외하고 최소 5개의 독립된 내용 상자를 배치한다. 제목, 거버닝 메시지, 요구사항 번호, 푸터, 구분선, 순수 장식은 내용 상자로 계산하지 않는다.

- 각 내용 상자는 범위, 전략, 절차, 구성요소, 통제, 성과처럼 서로 구별되는 역할을 맡는다.
- `3+2`, `2+2+1`, 위 2개+중간 2개+하단 결론 1개, 중앙 허브 1개+주변 노드 4개를 우선 검토한다.
- 좌우형이면 양쪽에 각각 내용 상자를 배치하고, 상하형이면 위아래 모두에 내용 상자를 배치한다.
- 하나의 문장을 다섯 박스로 나누거나 근거 없는 내용을 추가해 개수만 맞추지 않는다.
- 선택 에셋이 feedback loop, quality gate, hub-spoke, swimlane이면 해당 토폴로지의 노드와 연결 관계를 실제 상자 구조에 반영한다. 최소 수량을 채우기 위해 같은 카드 형태를 반복하지 않는다.

`block_pool_auto`를 사용할 때는 요구사항 내용에 따라 `matrix_table`, `metric_dashboard`, `scope_outcome_mapping`, `blueprint_flow`, `chevron_pipeline`, `gantt_roadmap` 중 필요한 타입을 조합한다. `blueprint_flow`는 `steps[]`마다 동일 순서의 `step_details[]`를 채워 처리 노드 내부의 상세 문구를 보존한다. 자동 배치는 타입별 최소 높이를 우선 보장하며, 세로 공간이 부족하면 내용을 축소하지 않고 먼저 장표를 시리즈로 나눈다. 네이티브 도식을 끝까지 구성해도 전달할 수 없는 경우에만 `text_explainer`로 전환한다.

## 5. 비교와 결론

비교·두 축·대안 블록은 항목 나열로 끝내지 않는다. `content.conclusion`에 선택, 통합 방식, 우선순위 또는 적용 결과를 한 문장으로 작성한다. 가능하면 `니다.`로 끝나는 실행 문장으로 쓴다.

## 6. 자산 재사용

원본이 가로형이거나 다른 업무 주제여도 구조와 미감이 적합하면 세로형에서 재사용한다. 크기, 배열, 라벨, 방향을 세로형 프레임에 맞춰 재구성한다.

최종 구현은 기본적으로 PowerPoint 네이티브 도형이어야 한다. 스크린샷, 래스터 이미지, SVG 직접 삽입, 편집 불가능한 그룹 그림, SVG를 변환한 뒤 그룹 해제하는 절차에 의존하지 않는다. 하나의 의미 모듈을 이루는 네이티브 도형과 텍스트는 이동·복제 편의를 위해 논리적으로 그룹화할 수 있다. 단, 사용자가 생성 이미지 사용을 허용한 복잡한 아키텍처의 `generated_visual_with_text`는 보조 시각 예외로 둘 수 있으며, 핵심 설명·수치·근거는 편집 가능한 텍스트로 별도 배치한다.

## 7. 복잡한 아키텍처

노드·연결·라벨을 읽을 수 없는 경우 작은 크기로 억지 배치하지 않는다. 핵심 흐름과 세부 관계를 가능한 한 담은 네이티브 도식을 끝까지 구성하고, 도식 아래에 `content.explanation` 부연설명을 붙인다.

1. `native_diagram`에서는 도식 라벨을 공간에 맞게 축약하되 출발 데이터, 주요 처리·통제, 전달 경로, 최종 사용자·운영 결과를 가능한 한 보존하고 부연설명으로 상세히 쓴다.
2. 네이티브 도식을 끝까지 구성해도 의사결정에 필요한 흐름을 전달할 수 없을 때만 `architecture_treatment: "text_explainer"`로 전환하고, 필요한 경우 `content.flow_steps`에 읽기 순서를 병기한다.
3. 사용자가 나노바나나/imagegen을 허용한 경우에만 `generated_visual_with_text`를 보조 이미지로 사용한다. 생성 이미지는 개념·분위기·큰 흐름만 보조하고, 정확한 라벨·수치·RFP 근거는 네이티브 텍스트에 둔다.
4. 텍스트 설명으로도 의사결정에 필요한 흐름을 전달할 수 없을 때만 와이어프레임 블록을 `architecture_required`로 표시하고 승인을 대기한다.

## 8. 최종 점검

- 거버닝 메시지가 `니다.`로 끝나는가?
- `요구사항 해석` 등 내부 표현이 보이지 않는가?
- 비교 블록이 무엇을 적용할지 결론을 말하는가?
- 큰 빈 상자 없이 RFP 근거가 충분히 담겼는가?
- 병렬 불릿이 가능한 경우 내용 도식으로 변환됐는가?
- 도식이 이미지가 아닌 PowerPoint 네이티브 도형인가?
- 논리적 그룹 내부에 이미지·SVG·미디어가 없고 그룹 해제 후 개별 편집 가능한가?
- PowerPoint 편집 화면에서 모든 도형과 라벨이 보이는가?
- 첫 와이어프레임에 장식을 제외한 독립된 내용 상자가 5개 이상이고 정보 밀도가 `high`이며, 이를 동일한 카드 반복으로 채우지 않았는가?
