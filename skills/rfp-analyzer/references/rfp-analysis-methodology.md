# RFP 정밀 분석 방법론 (RFP Analysis Methodology)

본 문서는 RFP(제안요청서, 과업지시서)를 검토할 때 기능요구사항, 업무 흐름, 플랫폼 구성요소, 제안사 관점에서 직접 수행이 어려워 보이는 영역을 일관된 기준으로 분석하기 위한 표준 작업 지침이다.

---

## 1. 작업 목적

RFP 분석의 핵심은 단순히 요구사항 목록을 옮겨 적는 것이 아니라, **고객이 실제로 수행하려는 목표 업무를 복원**하고, **RFP에 명시되지 않았지만 구축에 반드시 필요한 숨은 기능 요소를 찾아내는 것**이다.

분석 결과에는 다음이 명확히 드러나야 한다:
1. RFP가 요구하는 **고객의 목표 업무 및 시스템 흐름**
2. 요구사항이 속한 **기능 도메인 분류**
3. 도메인별 **세부 기능과 누락/숨은 기능**
4. 원문 표현과 단위를 100% 보존한 **정량 요구사항 및 KPI**
5. 제안사 역량 관점에서 **직접 수행이 어려워 보이는 영역(Gap & Risk Area)**

---

## 2. 기본 분석 절차 (7단계)

1. **RFP 개요 및 사업 목적 확인**: 발주기관, 사업명, 기간, 예산, 평가방식, 핵심 목적 파악.
2. **고객의 목표 업무 흐름 복원**: 단순 나열이 아닌 단계별 End-to-End 업무 흐름도 작성.
3. **업무 흐름에 AI/데이터/보안/운영 요소 결합**: AI 파이프라인을 분리하지 않고 업무 흐름 단계에 결합.
4. **요구사항을 행동 단위로 분해**: 사용자 행동과 시스템 반응으로 세분화.
5. **13대 기능 도메인 분류 및 8개 관점 상세화**: 사용자, 목적, 시작조건, 입력, 처리, 출력, 통제, 연결.
6. **숨은 기능 및 정량 KPI 3분류 추출**: 필수 확정치, 예시/권고치, 목표 미정 항목 분리.
7. **제안사 관점 실행 난도 영역(Gap) 평가**: `company_profile/`을 참조하여 파트너링 필요 영역 식별.

---

## 3. 목표 업무 흐름 복원 및 AI/데이터 결합

기능 목록을 바로 정리하기 전에 아래와 같은 공통 목표 업무 흐름을 기준으로 고객의 실제 절차를 복원한다:

```text
사용자 / 외부 시스템
  ↓
1. 데이터 등록 또는 연계 수집 (파일 수집, DB 연계, API 연계, 크롤링, 반입)
  ↓
2. 보안 검증 / 권한 확인 / 반입 승인 (MFA, 악성코드 검사, 반입 승인 워크플로우)
  ↓
3. 전처리 / 파싱 / OCR / 정제 (문서 파싱, 표 추출, 이미지/음성 처리, OCR, 클렌징)
  ↓
4. 메타데이터 추출 / 품질 점검 (프로파일링, 품질 규칙, 표준화, 계보 관리)
  ↓
5. 저장 / 인덱싱 / 벡터화 (레이크하우스, 검색 인덱스, 임베딩, Vector DB)
  ↓
6. 카탈로그 등록 / 검색 제공 (데이터셋 카탈로그, 하이브리드 검색, 접근제어)
  ↓
7. 분석 / AI 활용 / 업무 처리 (RAG, LLM, Agent, 모델 추론, 업무 로직)
  ↓
8. 결과 제공 / 다운로드 / 반출 승인 (보고서, API, 모델 배포, 반출 심사)
  ↓
9. 이력 / 로그 / 품질 피드백 (사용 로그, 검색 품질, 답변 평가, 모니터링)
```

---

## 4. 요구사항의 행동 단위 분해

RFP 문장 하나를 사용자 행동과 시스템 처리 단위로 쪼갠다:
* *예시 1*: "사용자는 계약서를 업로드한다" 
  → 파일 업로드, 형식 검증, 악성코드 검사, 저장소 저장, 버전관리, 업로드 이력 저장, 실패 시 오류 안내.
* *예시 2*: "담당자는 승인한다"
  → 승인/반려, 의견 입력, 이력 저장, 상태 변경, 알림 발송, 권한 검증.

## 5. 13대 기능 도메인 분류 기준

| 도메인 | 설명 | 주요 기능 예시 |
| :--- | :--- | :--- |
| **포털 / 사용자 접점** | 사용자가 시스템에 접근하고 업무를 시작하는 영역 | 로그인, 메인 대시보드, 메뉴, 공지, 마이페이지 |
| **사용자 / 권한 / 조직** | 역할과 권한을 관리하고 접근을 통제하는 영역 | 사용자 관리, 조직 연동, RBAC, 권한 승인 |
| **프로젝트 / 워크스페이스** | 과제 단위 업무공간과 자원을 관리하는 영역 | 프로젝트 생성, 멤버 초대, 자원 할당, 격리 공간 |
| **데이터 수집 / 연계** | 내부 및 외부 데이터를 가져오는 영역 | 파일 업로드, DB 연계, API 커넥터, 수집 스케줄 |
| **데이터 저장 / 관리** | 데이터를 구조화하여 저장하고 관리하는 영역 | 원천/정제 저장소, 레이크하우스, 메타데이터, 계보 |
| **데이터 품질 / 표준** | 데이터의 신뢰성과 일관성을 확보하는 영역 | 프로파일링, 품질 규칙, 표준 코드/용어 |
| **데이터 가공 / 라벨링** | AI 및 분석에 활용 가능하도록 가공하는 영역 | 파싱, 청킹, 비식별화, 라벨링, 전처리 |
| **검색 / 카탈로그** | 데이터, 문서, 모델, 결과물을 탐색하는 영역 | 키워드/벡터 하이브리드 검색, 필터, 카탈로그 |
| **AI 개발 / 학습** | 모델을 실험, 튜닝, 학습하는 영역 | 실험 관리, 파라미터 튜닝, GPU 자원 신청, 학습 |
| **AI 추론 / 배포 / 운영** | 모델을 서비스화하고 모니터링하는 영역 | 추론 API, 모델 서빙, 모니터링, 재학습 파이프라인 |
| **보안 / 반출입 / 감사** | 민감정보와 시스템 접근을 통제하는 영역 | 암호화, 마스킹, 반입/반출 승인, 감사로그 |
| **인프라 / 클라우드 / 운영** | 시스템 실행환경과 인프라를 운영하는 영역 | 서버, GPU, Kubernetes, 모니터링, 백업/복구 |
| **교육 / 전환 / 지원** | 시스템을 실제 사용하게 만드는 영역 | 사용자/운영자 교육, 매뉴얼, 기술이전, 안정화 지원 |

## 6. 도메인별 8대 관점 상세 분석

각 도메인은 다음 8가지 관점으로 빠짐없이 점검한다:
1. **사용자**: 이 기능을 사용하는 사람 또는 조직은 누구인가?
2. **업무 목적**: 이 기능으로 해결하려는 업무 문제는 무엇인가?
3. **시작 조건**: 기능이 언제, 어떤 조건에서 트리거되는가?
4. **입력**: 사용자가 넣거나 시스템이 받는 데이터는 무엇인가?
5. **처리**: 내부에서 어떤 검증, 변환, 계산, AI 처리가 일어나는가?
6. **출력**: 화면, 파일, API, 알림, 보고서 등 결과는 무엇인가?
7. **통제**: 권한, 승인, 보안, 이력, 예외 처리는 무엇이 필요한가?
8. **연결**: 다른 도메인이나 외부 시스템과 어떻게 이어지는가?

## 7. 정량 요구사항 및 KPI 3분류 추출 원칙

RFP에 흩어진 모든 정량 조건은 기능 설명과 분리하여 표로 추출한다.

* **수치 3대 분류**:
  1. **필수 (Mandatory)**: RFP가 충족 또는 준수를 명시한 확정 기준 (예: "응답시간 3초 이내", "가용성 99.9% 이상").
  2. **예시 (Guideline/Example)**: `예`, `예시`, `권고`로 제시되어 구속력이 확정되지 않은 수치.
  3. **목표 미정 (TBD)**: RFP가 KPI 수립을 요구하지만 목표값은 제시하지 않은 항목.
* **원문 보존 규칙**:
  * 원문의 표현과 단위(`value_text`)를 절대 변경하지 않는다.
  * 예시를 확정값으로 오인하여 기재하지 않는다.
  * RFP에 없는 신규 KPI나 가공된 목표값을 임의로 창작하지 않는다.

## 8. 제안사 역량 갭(Capability Gap) 평가 원칙

`company_profile/`의 정보를 참조하여 다음 기준에 따라 제안사 직접 수행 난도를 평가한다:
* 대규모 물리 HW, 스위치, 스토리지, GPU 클러스터 센터 납품/구축이 핵심인가?
* IaaS, PaaS, CMP, 가상화 등 인프라 플랫폼 구축 경험이 필수인가?
* 국방 K-RMF 인증, 보안통제 증적 평가, 국가용 암호장비 도입 경험이 필수인가?
* 특정 상용 패키지(ERP 등) 또는 하드웨어 장비 납품이 필요한가?
* 제안사의 핵심 역량만으로 충분한가, 아니면 협력사/컨소시엄 조달이 필요한가?
